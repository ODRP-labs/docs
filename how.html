Long Haul · the technical rundown

So you want to know how the sausage is made?

No pitch, no arguments, no "why." If you're reading this you already get the point — here's the how, from the ground up. Each piece is tagged built (proven in simulation), partial, or planned so you always know where the edge of reality is.

Start here

What is a puppet? built

Everything in Long Haul rests on one idea, so start with it.

In Reticulum, every endpoint is a destination. A destination is built from an Identity — a key pair — and that gives it two very different "names":

1

A destination hash — a 16-byte address derived from the Identity's public key. This is its real address, the thing Reticulum actually routes on. It can't be copied, forged, or duplicated without the private key.

2

A handle — a plain display label (your label / display name) that any node can set to anything. It is not an address. Twenty nodes can all call themselves "Bob."

A puppet is a brand-new, fully independent Reticulum destination that Long Haul creates and owns — its own Identity, its own keys, its own hash — that simply wears the handle of a node living on the far mesh. It is not a clone and it holds nobody else's keys. The only thing it borrows from the far node is the human-readable handle, so you recognize it.

Why it existsThe real far-side node lives on a mesh you can't reach directly. The puppet is a local stand-in you can address like any other contact — and because it's a genuine destination Long Haul owns, it can legitimately decrypt what you send it, as the true endpoint, not as a snoop.

The setup

How Long Haul stands puppets up built

Two gateways, one per site — call them LH1 and LH2. Each runs a normal, unmodified Reticulum node on its own mesh, and the two are joined only by the radio.

→

Roster sync. Over the HF leg, each gateway tells the other which nodes are currently present on its mesh — presence and handles.

→

Auto-puppet. For every node on the far mesh, the local gateway stands up a puppet (own keys/hash, far node's handle). When a node leaves the far mesh, its puppet is torn down. It tracks the far side automatically so the roster stays live.

→

The crossing. You address puppet ⟨Bob⟩ locally. That puppet is the endpoint, so it decrypts your message with its own keys, hands the cleartext to the modem, and it goes over HF as a plain framed byte pipe — not Reticulum, no Reticulum routing on that hop at all.

→

Re-origination. LH2 receives the bytes and re-originates: it injects a fresh, fully-encrypted Reticulum message into mesh 2, from a puppet of you, addressed to the real Bob. Mesh 2 routes it normally.

The load-bearing ideaReticulum routing never crosses the cleartext leg. Each gateway terminates one encrypted Reticulum network and re-originates into the other — a store-and-forward bridge between two healthy meshes, with a plain byte pipe in the middle. Nothing about Reticulum is modified or stripped.

Roster cadenceThe roster isn't a constant beacon: it's sent only when membership changes (a short burst), the channel stays silent when idle, and there's just a slow backstop refresh — currently about every three minutes, but that's a placeholder, not a tuned number, and likely a setting you'll be able to dial. A reliable ARQ link carries it along; a fire-and-forget link repeats it a few times, since there's no acknowledgement. Syncing less often means less airtime, less power draw, and less for a listener to watch — at the cost of slower presence updates.

Dropped framesOn the reliable ARQ path the modem guarantees the whole message. On fire-and-forget, each message carries a checksum: it arrives whole and verified, or it's dropped — never a half-message, and no request to resend. That keeps fire-and-forget fast and light, which is its whole point; if a message has to arrive, you send it over ARQ (the recommended mode).

Trust on an open channel

How do we know a transmission is really from our station? built

The HF leg is cleartext, and by law (Part 97) we can't encrypt it. So here's the fair worry: if anyone on the frequency can hear our frames, anyone could also transmit a frame that looks like it came from LH2. How does a gateway know a message it's about to inject into its mesh really came from our trusted partner station — and not from some mischief-maker with a radio?

The answer isn't secrecy. It's signatures.

What a signature is

The sending gateway computes a cryptographic signature (Ed25519) over the payload with its private key. The receiving gateway verifies it against the partner's public key, which the two trusted stations exchanged once when they paired (see below). If it doesn't verify, the frame is dropped. To stop anyone re-broadcasting a captured-but-valid frame, each message also carries a signed timestamp: the receiver rejects anything outside a freshness window, and a short cache catches duplicates inside it. The two gateways keep their clocks agreed with each other automatically — every signed frame is a fresh time sample — so this needs no external clock or GPS.

How the two stations pair built

So how do the two stations get each other's public keys in the first place — over an open channel where a mischief-maker could try to slip in their own? You pair them once, with a short one-time code. Both operators type the same code (say ten digits) into their gateways, and the two then run a PAKE (password-authenticated key exchange) over the air: the code is woven into the math, so only a party who knows it can complete the exchange, and a final check aborts if anyone tried to sit in the middle. Under that code-authenticated exchange the gateways swap and store each other's long-term signing keys — and the code is never needed again.

The one rule that keeps it safe: the code's secrecy is the trust. Anyone who has the code could pair as you, so you share it out-of-band (in person, a call, an encrypted message), never on the air — and if you ever think it leaked, you re-pair with a fresh one. Re-pairing is also how you rotate keys: if a gateway is lost or compromised, a fresh pairing replaces the trust cleanly.

How that's different from encryption

Encryption hides the content. A signature hides nothing — the message stays completely readable in the clear. It only proves two things: who sent it, and that nobody altered it in flight. Authentication, not obfuscation.

Is it legal?Yes. §97.113 bans messages "encoded for the purpose of obscuring their meaning." A signature obscures no meaning — the message is still plainly readable by anyone listening; the signature is just an appended authenticator riding alongside it. Signing proves origin; it doesn't hide the message, so it doesn't run afoul of the encryption rule.

A real trade-off

The signature is the gateway's, not the sender's built

Here's the honest catch, and it's a deliberate design decision. The signature is created by the gateway, not by the node that originally sent the message. So the far recipient can verify the message came from a trusted Long Haul station — but not that it came from the specific end user who typed it. Origin authenticity is vouched for by the two gateway operators, not by a true end-to-end signature.

Why we chose it that way

Because gateway-to-gateway signing requires zero modification of Reticulum. Each mesh runs stock, unmodified Reticulum; the signing lives entirely inside Long Haul, at the edge. True end-to-end signing would mean changing the Reticulum nodes and clients themselves — and the whole discipline of this project is don't touch Reticulum. So the trade is: in a closed, trusted group you trust the two Long Haul stations (and their operators). That's the deliberate, accepted cost of leaving Reticulum untouched.

Where this standsSignatures, the freshness window, and PIN pairing are built and verified in simulation: the gateway now refuses any frame that is unsigned, from an unknown key, forged, tampered, replayed, or stale, and a hostile-frame test exercises every one of those classes. What's left is the real bar — it has run only in simulation, never on air, and the pairing exchange gets a fresh security review before the first on-air use. So the air leg is authenticated today in software; treat it as proven-in-sim, on-air-pending.

A fine point people ask about

Why send the handle over the air, not the hash? built

Reticulum routes on the hash, so it's a fair question: why does the bridge address the far side by handle?

Because the hash isn't portable across the two meshes. A puppet has its own hash — different from the real node's hash — so the hash is not a shared identifier between a node and its puppet. The one thing they have in common is the handle. It's the single stable name both sides already agree on, so that's what the bridge uses to say "this one's for Bob."

Resolving it on the far side is simpler than it sounds — there's no shared lookup table to keep in sync or to attack. Each gateway just watches the ordinary announces on its own mesh and keeps a local handle → real-destination map. When a message crosses for "Bob," the far gateway looks "Bob" up in that local map and hands off to the real Bob like any normal local delivery. The map builds and maintains itself from announces each side already hears; neither gateway ever ships its routing table over the air.

To be exactInside each mesh, routing still uses the real destination hash, exactly as normal Reticulum does. The handle is only the cross-bridge addressing key — it never replaces the hash for local routing, and the hash never rides the air.

Handle collisionsBecause the handle is the addressing key, two nodes with the same handle are a problem — and the hard part isn't the routing, it's a human telling two "Bob"s apart. Long Haul handles it at the source, first come first served: the node that picks a handle already in use anywhere across the two bridged meshes gets a message from the Long Haul node — "handle already in use; far-side delivery unavailable until it's unique." It can't force-rename you, but it's a real opt-out: while your handle collides, Long Haul routes nothing for you in either direction until you fix it — and the original holder of the name is never affected. If a collision still slips through, the gateway refuses to silently guess and flags it rather than misrouting. Today, on-air routing uses the handle itself (kept unique by that rule); the finished-product goal moves it to a short rotating token, so a permanent tag never has to ride the air at all — which is also what makes your roster and traffic pattern private to outside listeners.

What tokens can't hideEven once routing rides rotating tokens, an outside listener still sees message sizes and timing — who transmits, when, and how much. Hiding that (padding every message, sending cover traffic) costs bandwidth a ~100 B/s link can't spare, so it's an accepted residual: the tokens hide who you are, not that a transmission happened.

The last details

Callsign, layers, and why every frame

Where the callsign lives built

Station ID lives at the modem-driver layer, not the message stack — because a callsign identifies the transmitter, not the message. One transmission is one frame, laid out like this:

[ payload ][ signature ][ callsign trailer ]
   \__________/   \_________/   \_______________/
    the message    proves the    DE <call> — the
    (cleartext)    sender         operator's station ID

The signature covers the payload only, never the callsign. That's on purpose: a relay may re-stamp its own callsign as it re-sends (third-party traffic, §97.115), so the callsign has to be mutable hop-to-hop — if the signature covered it, every relay would break the signature. Callsign last, so it's literally the last thing on the air.

Why every frame, not just end-of-transmission built

The callsign (DE <call>) is appended to every frame, WSPR/FT8-style. Doing it that way auto-satisfies both §97.119 rules at once — the end-of-transmission ID and the 10-minute ID — with no timer to run or forget. It also just works for fire-and-forget, where there's no clean "end of transmission" to hang an ID on. Plus a hard gate: a transmitter with no callsign set refuses to key at all.

Adversarial mode built

One switch takes Long Haul out of the message path — no more puppets, no decrypt-and-re-originate — and lets native, fully-encrypted Reticulum ride straight over the modem, for the day the rules no longer apply. The advantage of a switch over ripping Long Haul out is that it stays in as the plumbing: it still handles the port wiring, the node and modem connection, ALE frequency selection, and the rest of the transport setup. So you flip one flag and everything is already wired — instead of hand-configuring Reticulum onto the radio from scratch on the day you need it most.

StatusThe flip is built and, thanks to a turn-aware modem shim, so is delivery: a Reticulum message now crosses both ways in the encrypted mode (~66 s in simulation), with a tap on the modem port confirming only ciphertext leaves and no station ID or readable metadata riding along. The shim fragments each packet to the modem's frame and TDMA-paces the two half-duplex stations so they don't key over each other. Caveats, said plainly: proven in simulation only, never on air; V1 is Mercury broadcast + opportunistic messages only (Direwolf/AX.25 and ARQ modems still need their own shims); the data cap is not enforced in this mode, since Long Haul is out of the path; and the legal-gate modal wording is a draft pending attorney review.

The UI built

Two-sided config: one side connects to your Reticulum node, the other picks your modem and its settings. The piece that turns a working proof into something an operator can actually run.

Long Haul is a node you can talk to built

Long Haul isn't just an invisible pipe. It stands up its own destination on the mesh — the same way it makes puppets — so it shows up in any normal Reticulum client as a contact called "Long Haul," and you message it like anyone else. That's the channel for the rest of this: the handle-collision nudge arrives as a DM from it, C2 commands are DMs to it, and data-cap bounces and status readouts come back from it. Each gateway has its own on its own mesh — you talk to your local Long Haul for local settings, and it relays across the hop to reconfigure the far one.

Data caps built

HF is slow — on a clean channel Long Haul moves roughly 100 bytes a second, so a 200 KB photo is about half an hour and something bigger could tie up the leg for the rest of the day. So each link gets a data ceiling — and it's yours to set, not some fixed number baked in. You tune the cap to your band, your modem, and how your group actually uses the link: raise it on a fast, quiet channel; clamp it down when conditions are marginal or the leg is busy. (And per the section below, you can change it remotely, on either gateway.)

Today the gateway already paces its writes to the modem's own queue so nothing overruns it built. The operator-facing half is built too: address a puppet with something over the cap and the puppet answers you right back — on your own mesh, instantly — with a plain error like file exceeds the HF limit — compress or split and resend. The oversized message bounces at the puppet, before the radio ever keys, so you find out on the spot instead of burning airtime discovering it.

Command & control built

An unattended station you can't walk over to still needs managing — you do it by messaging the Long Haul node itself (above). Because C2 rides on the signature layer, a command is just authenticated traffic — a signed instruction instead of a signed message. No new mechanism, and legal the same way signatures are (cleartext, just authenticated).

What you'll be able to set remotely: ALE settings, the data caps above, and the other variables Long Haul manages. And it works in both directions — you can reconfigure your local gateway (the in-mesh instance) or reach across the hop to reconfigure the far gateway (the cross-hop instance). So an operator can tune a station on the far end of the country without leaving home, and every command carries proof it came from you.

And it's gated. Changing Long Haul's settings is not open to just anyone on the mesh — only the station owner, or users the owner has authorized, can do it, behind a login / verification step. Ordinary mesh users send and receive traffic freely; reconfiguring the gateway is a privilege, not a default.

StatusThe near-side half is built: you DM your local Long Haul node and it answers status, arms pairing, re-announces, sets the data cap, switches the modem, and restarts — gated to allow-listed nodes and audited. And the far-side half is built too: the settings the two paired gateways share — the modem/band, the data cap, and the operating frequency — now change on both sides at once through a safe, signed handshake with auto-revert. If the new setting doesn't re-establish contact, each gateway independently rolls back to the last-known-good — and because the channel itself is what changed, the revert can never be a message over the (possibly dead) new link. Proven in simulation; the only leftovers are a read-only peek at the far gateway's status and a small ack layer for coordinating over fire-and-forget.

Browse NomadNet pages & files over the radio built

NomadNet is Reticulum's built-in web — pages and file shares that nodes host for each other. Long Haul carries the read/download half across the HF bridge: it puppets a far NomadNet node on your mesh, so browsing that puppet turns each page or file fetch into a signed request relayed over the radio — the far gateway pulls the real page from its own local mesh and relays the bytes back. Because pages and files are public content, the relay is cleartext, station-ID'd, and data-cap bounded — §97-clean like everything else (sign, don't encrypt). It's slow over HF (a page is several radio frames of seconds each, so a holding page shows while it fetches), and an over-cap file is refused with its name and size before the radio ever keys. Proven in simulation against a real NomadNet node. V1 is static pages + file downloads — no scripts or forms, no hopping off to other nodes; and it's not voice, not transparent transport.

Encrypted-content guard built

The whole legality of Long Haul rests on cleartext going out over the air. It strips Reticulum's own encryption — but a file someone already encrypted with outside tools (a GPG/age blob, an encrypted zip) would still be ciphertext after that strip, and putting that on the air is illegal. So a guard screens every message and file at the transmit edge and refuses to key the radio with anything that looks encrypted, bouncing a plain reason back to the sender. It knows the common encryption signatures, passes legitimate binaries (JPEG/PNG/PDF/media) so they aren't false-flagged, and catches leftover near-random blobs by their randomness. Honest limit: perfect detection is impossible — it can't see inside every container or stop a deliberate evader — so it's a best-effort guard against honest mistakes, and the licensed operator stays responsible. It fail-closes, and can be set to reject / warn / off.

Turning the radio's dial built

Long Haul owns the modem; optionally, it can own the radio's dial too. Through hamlib it reads and sets the rig's frequency and mode — and every set reads the value back off the radio and reports what the dial actually did, never a number it just assumed. That unlocks a coordinated QSY: change frequency on one gateway and both paired stations re-dial together at a shared instant, with the same auto-revert as a modem change — if the new frequency doesn't re-establish contact, both roll back. It only tunes inside operator-configured allowed band segments (empty = refuse everything; Long Haul invents no band edges it has no authority over) and is off by default. Proven in simulation against hamlib's dummy rig — not yet on a real radio.
